# 千兆网与低延迟配置

最后确认：2026-07-13

## 是否自行编写网络协议

第一版确定使用 ROS2 DDS + QoS，不自行编写 UDP/TCP 协议。每帧球状态只有数百字节，
在千兆直连网络上带宽可忽略。自行实现协议还需要重新处理序列化、字节序、版本兼容、
发现、重连、丢包、乱序和时间戳，收益很小。

若实测 DDS 单向延迟或抖动不能满足要求，再评估 Zenoh/自定义 UDP；切换传输层时保持
上述消息语义不变。验收目标建议为：NX 采集到 RDK 回调中位延迟小于 10 ms，P99 小于
20 ms，无持续旧消息积压。

## 静态 IP

使用独立千兆网口直连，建议网段：

```text
NX : 10.42.0.10/24
RDK: 10.42.0.20/24
```

该网段不配置默认网关和 DNS，避免改变设备原有上网路由。接口名称先用 `ip -br link`
确认，以下以 `eth0` 为例。

NetworkManager 配置示例：

```bash
# NX
sudo nmcli con add type ethernet ifname eth0 con-name nx-rdk-static \
  ipv4.method manual ipv4.addresses 10.42.0.10/24 ipv6.method disabled
sudo nmcli con up nx-rdk-static

# RDK
sudo nmcli con add type ethernet ifname eth0 con-name nx-rdk-static \
  ipv4.method manual ipv4.addresses 10.42.0.20/24 ipv6.method disabled
sudo nmcli con up nx-rdk-static
```

若连接已存在，应使用 `nmcli con mod`，避免创建重复连接。验证：

```bash
ip -br address show eth0
ethtool eth0
ping -I eth0 10.42.0.20   # NX执行
ping -I eth0 10.42.0.10   # RDK执行
```

`ethtool` 必须显示 `Speed: 1000Mb/s`、`Duplex: Full`、`Link detected: yes`。

## DDS 网卡绑定

两端必须使用相同：

```bash
export ROS_DOMAIN_ID=42
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
```

推荐 Cyclone DDS，并通过配置只绑定直连网卡地址，避免 Wi-Fi、Docker 和其他网卡参与
发现。`~/cyclonedds.xml`：

```xml
<?xml version="1.0" encoding="UTF-8" ?>
<CycloneDDS xmlns="https://cdds.io/config">
  <Domain Id="any">
    <General>
      <Interfaces>
        <NetworkInterface address="10.42.0.10" priority="default" multicast="default"/>
      </Interfaces>
      <AllowMulticast>true</AllowMulticast>
    </General>
  </Domain>
</CycloneDDS>
```

NX 使用 `10.42.0.10`，RDK 文件改为 `10.42.0.20`。然后：

```bash
export CYCLONEDDS_URI=file://$HOME/cyclonedds.xml
```

若直连环境的组播被系统或交换机限制，可改用 Cyclone DDS 静态 peers，双方互填对端
IP；不要同时绑定不相关接口。

## 时间同步

坐标补偿使用相机采集时刻，因此 NX、RDK 和底盘时间必须一致。首选 PTP：RDK 作为
时间主机，NX 作为从机；无硬件时间戳时可先使用软件 PTP 或 Chrony。要求：

- 正常偏差小于 1 ms；
- 超过 5 ms 时控制节点降低 NX 数据可信度并报警；
- 超过 20 ms 时拒绝远场数据进入控制。

需要持续发布 `/diagnostics/time_sync` 或写入状态日志，记录时钟偏差、消息年龄和网络
延迟。只有发送与接收使用同一时钟基准时，`now-header.stamp` 才表示真实延迟。

本项目使用 `volleyball_interfaces/TimeSyncStatus`，其中
`offset_ns = NX时钟 - RDK时钟`。默认要求状态在 0.5 s 内更新、估计不确定度不超过
2 ms；控制节点使用修正后的 NX 采集时间查询 odom。NX 双目消息的左右采集时间差默认
不得超过 1 ms。

## 系统与程序低延迟要求

- 视觉话题 QoS depth 固定为 1，控制节点只处理最新消息。
- 不通过该实时链路发布原始图像或完整深度图；调试图像使用独立开关和低频 QoS。
- NX 发布采集时间戳，不能覆盖为推理完成时间。
- RDK 丢弃乱序消息和超过 `nx.timeout_s` 的消息。
- DDS 回调只覆盖最新消息缓存；坐标变换、滤波和 RK4 预测由独立100 Hz控制循环执行。
- 控制循环建议 100 Hz；NX/D435 消息到达时更新缓存，控制循环读取最新快照。
- 日志使用节流，避免每帧同步输出终端。
- 预测 Path 等诊断话题使用 Best Effort，并限制在 10–20 Hz。
- 网口收发错误、丢包和 DDS deadline miss 应进入诊断。

不建议第一阶段启用 Jumbo Frame。标准 MTU 1500 对小型状态消息延迟更稳定，也避免两端
MTU 不一致。只有未来传输大图且完整链路验证后才考虑 MTU 9000。

## 联调验收

1. `ping` 连续 10 分钟无丢包，时延稳定。
2. `ethtool` 确认千兆全双工，无 RX/TX error 持续增长。
3. `ros2 topic hz /nx/ball/observation` 达到 NX 发布频率。
4. 记录 `receive_time-header.stamp` 的中位、P95、P99。
5. 模拟拔网线：RDK 不阻塞，并在 0.30 s 后撤销远场目标。
6. 恢复网络：旧消息不得重放触发新周期。
7. 验证 `/auto/goal_pose` 全系统只有 `catch_controller` 一个发布者。
